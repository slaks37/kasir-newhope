# Laporan QA & status perbaikan — 2026-10-04

Basis: `main@3c6de32`. Perbaikan: PR 1 `cto/stabilization` dan PR 2 `cto/stabilization-2` (bertumpuk di atas PR 1). Langkah rilis: [runbook](../operations/runbook-2026-10-stabilization.md). Keputusan produk yang tersisa: [dokumen desain](../design/2026-10-keputusan-produk.md).

## Metode
- **Statis**: typecheck seluruh tree, hygiene, semua suite test, pembandingan bundle Vercel dengan source.
- **Dinamis**: stack lokal (`npm run dev`, PGlite) + build produksi frontend, auth tiruan Supabase, browser di-drive lewat DOM, proxy yang bisa memutus jaringan dan **membuang ACK** setelah server commit.
- **Volume**: 10 / 1.000 produk; 100 / 10.000 / ±100.000 transaksi (±250.000 item) lewat API asli. `EXPLAIN ANALYZE` pada query laporan.
- **Load**: 1 / 5 / 10 / 50 kasir virtual bersamaan (jual → poll state → laporan hari ini).

**Batasan**: PGlite berjalan satu thread dan tidak menjalankan autovacuum/ANALYZE, sehingga angka absolut dan angka load adalah **batas bawah**. Bentuk query plan dan rasio sebelum/sesudah berlaku juga di Postgres. Ulangi load test di staging Postgres.

Load 50 kasir (sebelum index, DB berisi tenant 100k trx): laporan p50 8,4 dtk, 15% 503, kirim transaksi p95 6,3 dtk. Pemicunya: query laporan memindai `transaction_items` milik **semua tenant**.

> **Koreksi metodologi.** Statistik tabel di PGlite tidak pernah dianalisis, sehingga sebagian waktu "sebelum" juga dipengaruhi rencana query yang buruk. Setelah `ANALYZE`, query laporan aplikasi dengan index turun dari ±37 dtk ke 220 ms. Uji "tanpa index + statistik segar" tidak selesai dalam 30 menit, jadi index tetap akar masalah utamanya. Di Postgres produksi autovacuum aktif; ulangi pengukuran di staging.
